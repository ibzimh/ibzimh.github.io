Last month I needed to read dates out of a plain text file. Nothing exotic: lines that began with something like `2026-04-11 09:30`, followed by whatever I had written that day. My first instinct was to install a date library. My second, which won, was to see how small a parser could be if it only supported the one format I actually use.

## Start with what you accept

Most of the trouble with parsing comes from accepting too much. A general date library has to understand every calendar, every locale and every way a person might type “next Tuesday”. I only had to understand one shape: four digits, a dash, two digits, a dash, two digits, and optionally a space and a time. Writing that sentence down took a minute, and it turned out to be the whole specification.[^1]

A specification this short has a pleasant side effect. Every input is either inside it or outside it, and there is nothing in between to argue about.

## Writing the parser

A regular expression is enough here, because the format has no nesting. I let it do the matching, turn the captured pieces into numbers, and hand them to the built-in `Date` constructor.

```js
const PATTERN = /^(\d{4})-(\d{2})-(\d{2})(?: (\d{2}):(\d{2}))?$/;

function parseDate(text) {
  const m = PATTERN.exec(text.trim());
  if (!m) {
    return { error: `Can't read "${text}"` };
  }

  const [year, month, day, hour, minute] =
    m.slice(1).map((n) => Number(n ?? 0));
  const date = new Date(year, month - 1, day, hour, minute);

  // new Date rolls 2026-02-31 over to March, so check it didn't
  if (date.getMonth() !== month - 1) {
    return { error: `${text} isn't a real day` };
  }
  return { date };
}
```

Two details are worth pointing out. The function returns an object with either `date` or `error` instead of throwing, so the caller decides what a bad line means. And the check near the end exists because `new Date` is polite to a fault: ask it for the 31st of February and it quietly gives you the 3rd of March.

> A parser that says no clearly is worth more than one that says yes to everything.

## What I left out

No time zones, no two-digit years, no month names. Each one is a few more lines and a few more ways to be wrong, and I haven’t needed any of them. When I do, I’ll know exactly where to put them, because the pattern at the top of the file says what the parser promises and nothing else.

The part I enjoyed most was the testing. With so small a grammar I could list the awkward inputs in a minute: an empty string, a missing zero, a leap day, a day that doesn’t exist. Eight lines of tests covered every branch, and I trust them more than I trusted a library’s thousands of cases, which were mostly testing things I never use.

I would still reach for a library the moment the requirements grow past one format. The point isn’t that libraries are bad. It’s that the afternoon I spent was cheaper than the reading I would have done to learn one, and I came out knowing what my own code does.

[^1]: Writing the format out in one sentence first is a habit from my work log. If I can’t say what the input looks like, I’m not ready to write the code.
